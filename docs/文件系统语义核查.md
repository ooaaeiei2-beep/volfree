# volfree 文件系统语义核查

核查日期：2026-10-28
核查对象：volfree 中所有影响「判定是否安全」的逻辑
核查方法：本机 man 手册原文 + 官方规范原文 + 真机实测（APFS 与 exFAT 各一组）

---

## 一、结论摘要

最初有 7 条判断影响安全判定，其中 **3 条是错的**，1 条表述不准，1 条未能复现，2 条成立但理由需要换。

| # | 原判断 | 结论 | 依据 |
|---|---|---|---|
| 1 | macOS 的 lsof 不标注已删除文件 | **成立** | lsof(8)：`(deleted)` 后缀是 Solaris 专属，需 `-X` |
| 2 | `stat` 返回 ENOENT ⇒ 文件已删除、结束进程零风险 | **错** | ENOENT 只证明「没有名字指向它」，不证明「数据可弃」 |
| 3 | 已删除句柄的进程杀掉一定不丢数据 | **错** | 已删除 + 可写句柄 = 有进行中的写入被放弃 |
| 4 | APFS 有日志、exFAT 没有 | **表述错** | APFS 全文 0 次 "journal"，用 CoW + checkpoint + 校验和 |
| 5 | 卸载用 `diskutil unmount` 就够 | **不完整** | 手册：只有 `eject` 才让可移动介质「可安全手动取出」 |
| 6 | 进程用 mmap 写入时 lsof 完全看不见 | **错** | lsof 会为映射文件报 `fd=txt` 条目；丢的是「可写性」，不是「进程」 |
| 7 | 强卸载会损坏文件系统 | **未复现** | 实测 APFS/exFAT 强卸载后 fsck 均通过、文件逐块完好；真正的伤害是写入被立刻掐断 |

## 二、逐条证据

### 1. lsof 的删除标记 —— 成立，但正确工具是 link count 不是 stat

`man lsof` 原文：

> When `+L` is followed by a number, only files having a link count less than that number
> will be listed. A specification of the form `+L1` will select **open files that have been
> unlinked**. A specification of the form `+aL1 <file_system>` will select unlinked open
> files on the specified file system.

> `k` — link count

`(deleted)` 后缀的原文：

> Lsof may add two parenthetical notes to the NAME column **for open Solaris 10 files**:
> `(?)` … and `(deleted)` if the `-X` option has been specified

⇒ macOS 不会标注 `(deleted)`，这一点原判断成立。
但**官方给的判定手段是 link count（字段 `k` / 选项 `+L1`）**，不是我自造的 `stat` 事后校验。

### 2. ⚠️ link count 在 exFAT 上失效 —— 这是本次最重要的发现

实测：同一个「打开→删除→继续持有」的模式，分别在 APFS 和 exFAT(fskit) 上跑。

| | APFS | exFAT (fskit) |
|---|---|---|
| `lsof -F pcfk` 报的 link count | `k0` ✓ | **`k1` ✗（应为 0）** |
| `lsof -a +L1` 能否选中 | 能 ✓ | **选不中，返回空 ✗** |
| `stat` 该路径 | ENOENT | ENOENT |
| NAME 列有无 `(deleted)` | 无 | 无 |

```
# APFS
Python 31118 xushuda  6r REG 1,16 4096 0 173259255 /private/tmp/vfapfs/read_unlinked.bin
                     ↑ FD          ↑ NLINK=0

# exFAT
Python 30685 xushuda  6r REG 1,23 4096 1 18 /Volumes/VfFsCheck/read_unlinked.bin
                     ↑ FD          ↑ NLINK=1  ← 文件已删除，却报 1
```

**后果**：如果按官方推荐用 `+L1` 检测，在 exFAT 上会**一个都选不中**，工具会输出「无占用」——
这是最危险的假绿。原始故障恰恰发生在 exFAT 上。

⇒ 在 exFAT 上，`stat` 的 ENOENT 是**目前唯一可用的信号**，不是我图省事。

### 3. ⚠️ ENOENT 不等于「可以安全杀掉」

`stat` 返回 ENOENT 只证明一件事：**没有任何目录项指向这个 inode**。
它**不**证明：

- 进程没有正在往这个 inode 写；
- 这次写入没有价值。

典型的反例是 mkstemp + unlink 模式：先创建、立刻 unlink、然后持续写入。此时：

- `stat` 必然 ENOENT
- 但 fd 是可写的，进程正在往里写
- 杀掉进程 → 这次写入被放弃，而且因为文件没有名字，**没有任何其他途径能找回**

所以正确判据必须是**二维**的：link 状态 × 访问模式。

| | 只读句柄 | 可写句柄 |
|---|---|---|
| **仍有名字**（linked） | 谨慎：只丢程序内存态 | 危险：可能留下截断/半写的文件 |
| **已无名字**（unlinked） | 安全：数据已不可达，无写入 | **危险**：有进行中的写入会被放弃 |

原代码是 `has_write` 先于 `all_deleted` 判断，二维结果是保守的（已删除+可写 → RISKY），
**没有造成假绿**，但理由文案写错了：那种情况不会「损坏正在写入的文件」，因为已经没有文件了。

### 4. APFS 不是「有日志」，exFAT 才是真正没有事务

Apple《Apple File System Reference》(2020-06-22, 181 页) 原文：

> Within a container, the **checkpoint mechanism and the copy-on-write approach to modifying
> objects enable crash protection**. In-memory state is periodically written to disk in
> checkpoints, followed by a copy of the container superblock at that point in time.

> At the end of each transaction, new state is saved by writing a checkpoint.

> `o_cksum` — The **Fletcher 64 checksum** of the object.

全文检索结果：**"journal" 出现 0 次**。

⇒ APFS 没有日志，靠的是**写时复制 + checkpoint + 每个对象自带 Fletcher-64 校验和**。
崩溃时未提交的 checkpoint 被丢弃，回退到上一个一致状态。

Microsoft《exFAT File System Specification》§1.5 原文：

> **TexFAT is an extension to exFAT that adds transaction-safe operational semantics on top of
> the base file system.** TexFAT is used by Windows CE. TexFAT requires the use of the two FATs
> and allocation bitmaps for use in transactions.

⇒ 规范自己承认：**基础 exFAT 不是事务安全的**，事务安全是一个只有 Windows CE 用的可选扩展。

**这才是两者真正的差别**：不是「有无日志」，而是「元数据提交是否原子」。
exFAT 就地改 FAT 和目录项，断电/强卸载可能留下撕裂状态；APFS 提交是 checkpoint 级的，要么新要么旧。

### 5. 卸载与推出：`unmount` 不等于可以拔线

`man diskutil` 原文：

> `unmount | umount [force] device`
> Unmount a single volume. Force will force-unmount the volume (**less kind to any open files**).
> Up to a few seconds (or more) may be required for any Disk Arbitration dissenters in the system
> to approve the unmount, **and/or for the file system to flush data**. This verb gives up and
> returns failure after a maximum of **1 minute** in most situations.

> `eject [force] device`
> Eject a disk. … **removable media will become eligible for safe manual removal**; automatically-
> removable media will begin its physical (motorized) eject sequence. The disk's volumes will
> first be unmounted.

`man umount` 原文：

> `-f` The filesystem is forcibly unmounted. Active special devices continue to work, but all
> other files return errors if further accesses are attempted.

⇒ 三条修正：
1. **`unmount` 本身是刷盘的地方**，它失败是安全信号，不是麻烦。
2. 手册明说最多可能要 **1 分钟**，原代码 `run()` 默认超时 **20 秒** → 会误报失败。
3. 对 U 盘，`unmount` 之后设备仍通电；**只有 `eject` 才进入「可安全手动取出」状态**。

### 6. ⚠️ mmap 写入：lsof 看得见进程，看不见可写性

先纠正本文初稿的一个错误判断。初稿写「进程用 `PROT_WRITE` 映射一个只读打开的文件并修改，
lsof 仍报 `r`」——这个机制**不成立**。实测（`mmap(2)` 直调，APFS）：

```
O_RDONLY + PROT_WRITE + MAP_SHARED   -> 失败 errno=13 (EACCES)
O_RDONLY + PROT_WRITE + MAP_PRIVATE  -> 成功（写时复制，永不落盘，无害）
O_RDWR   + PROT_WRITE + MAP_SHARED   -> 成功
```

内核不允许「只读 fd 配可写共享映射」，那个场景根本构造不出来。

但真正的问题比初稿说的更隐蔽：**lsof 会为映射文件报一个 `fd=txt` 的条目，可它的 access
字段恒为空**，于是 volfree 的 `is_writing`（判 `"w" in access or "u" in access`）必然为假。

实验装置：`mmap(2)` 直调（绕过 Python `mmap` 模块对 fd 的持有），每 0.3 秒写一次并 `msync`，
同时调用 volfree 自己的 `scan_blockers()` + `assess()`。**APFS 与 exFAT 结果完全一致**：

| 写法 | 文件在变 | lsof 报的句柄 | volfree 判定 | 应为 |
|---|---|---|---|---|
| 普通 write，fd 打开 | 是 | `4u` access=`u` | RISKY | RISKY ✓ |
| mmap，fd 保持打开 | 是 | `txt` + `4u` | RISKY | RISKY ✓ |
| **mmap 后 close(fd)** | **是** | **只有 `txt`**，access=`''` | **CAUTION** | **RISKY ✗** |
| Python `mmap` 模块后 close | 是 | `txt` + `5u`（模块自己 dup 了 fd） | RISKY | RISKY ✓ |
| 只读 mmap，fd 打开 | 否 | `txt` + `4r` | CAUTION | CAUTION ✓ |
| 只读 mmap 后 close | 否 | 只有 `txt` | CAUTION | CAUTION ✓ |
| **mmap + close + unlink** | **是** | 只有 `txt`，`exists=False` | **SAFE** | **CAUTION ✗** |

两处错误，方向都是**低估风险**：

1. 有名字 + mmap 写入 → 判 CAUTION（理由「持只读句柄」），实际终止会留下**截断的现存文件**，
   这正是 RISKY 的定义。界面会给「安全结束并推出」，用户一点就切断了正在写盘的文件。
2. 无名字 + mmap 写入 → 判 **SAFE**（理由「终止不会丢失任何数据」），实际会丢弃一次进行中的
   写入且无法找回。这是本文档反复强调要杜绝的**假安全**。

`mmap + close + unlink` 的文件已无名、外部读不到，因此从映射读回以证明写入确实发生：
`READBACK b'M000022.........'`。

好消息是常见路径没坏：**Python 的 `mmap` 模块会 dup fd**，所以 `pymmap_close` 仍报 `5u`、
判 RISKY。缺口只出现在「`mmap(2)` 之后主动 close fd」的写法上——为省 fd 配额、或刻意只要
映射不要 fd 的程序会这么做。

**可精确修复**：映射的保护位能由 `proc_pidinfo(PROC_PIDREGIONPATHINFO)` 取到，与 `vmmap`
逐字一致：

```
proc_pidinfo:  prot=rw-  max=rwx      vmmap:  rw-/rwx     ← 可写映射
proc_pidinfo:  prot=r--  max=r-x      vmmap:  r--/r-x     ← 只读映射
```

⇒ 对 `fd == "txt"`、type 为 REG、名字落在本卷的句柄，补一次 `proc_pidinfo` 读
`pri_protection` 的 `VM_PROT_WRITE` 位即可区分。不需要解析 `vmmap` 文本，也不需要起子进程。

### 7. 强卸载：不损坏文件系统，但会立刻掐断写入

装置：在临时卷上铺底（1 个已 fsync 的 1MB 文件 + 6 个已 fsync 的小文件），然后持续追加写入
且**不 fsync**，2 秒后 `diskutil unmount force`，再以 `-nomount` 重新挂上、对**设备节点**跑
`fsck -n`、挂载后逐块校验。

| | APFS | exFAT (fskit) |
|---|---|---|
| `diskutil unmount force` | exit 0 | exit 0 |
| 写进程收到 | `EIO` (errno 5) | `ENXIO` (errno 6) |
| `fsck -n` 退出码 | **0** | **0** |
| 已 fsync 的 safe.bin | 1MB 完好 | 1MB 完好 |
| 正在写的 growing.bin | 382 块，逐块校验**无撕裂** | 370 块，逐块校验**无撕裂** |

APFS 的 fsck 输出里能看到它回退到 `checkpoint with transaction ID 25`，与第 4 条的
checkpoint 机制对得上。

⇒ 三条结论：

1. **强卸载本身不损坏文件系统**。它只跳过「等待不同意卸载的进程」，文件系统仍会收尾刷盘。
   「强卸载会毁盘」在本机可复现的范围内**不成立**。
2. **真正的伤害是写入被立刻掐断**。写进程在 2 秒处直接拿到 EIO/ENXIO，此后一行都写不进去；
   它缓冲区里还没交给内核的数据全部丢失，而程序未必知道要提示用户。
3. **`hdiutil detach -force` 在有进程持卷时会失败**（exit 1），所以「拔线/断电」无法用 dmg
   复现，见下一节。

这也修正了 volfree 拒绝强卸载的**理由**：不是「会毁盘」，而是「会让正在写的程序丢数据，
而且它可能不知道」。

## 三、仍未验证的地方（必须写进工具的限制说明）

1. **rename 竞态**。lsof 取名字和 `stat` 校验之间有窗口；若期间文件被重命名，会得到 ENOENT。
   实测 macOS 的 lsof 报的是**当前名**（重命名后立即显示新名），所以这个窗口很窄，但不为零。
2. **fskit 为何把已删除文件的 link count 报成 1**，没有官方文档解释，只有实测。
   可能是用户态驱动的实现取舍。这意味着未来 macOS 版本可能改变行为，**不能假设它永远如此**。
3. **exFAT 目录项是否有 SetChecksum**。规范里 File Directory Entry 确实定义了校验和字段，
   但我没能取到原文逐句确认，因此本文不据此下结论。
4. **真正拔线/断电的损坏形态**。`hdiutil detach -force` 在进程持卷时直接失败，
   `diskutil unmount force` 又会刷盘收尾，所以 dmg 上**无法复现**「不给文件系统任何机会」的断电。
   规范只说 exFAT 非事务安全，没描述撕裂后的恢复行为。这一条只能靠真实 U 盘插拔或断电测试，
   本机做不到，因此不作任何断言。
5. **采样与动作之间的窗口**。`proc_pidinfo` 能看到已建立的映射，但若进程在 volfree 采样与卸载
   之间**新建**映射，仍有窗口。与第 1 条同类，属 TOCTOU，无法用单次快照消除。

## 四、由此产生的修正

| 修正 | 说明 |
|---|---|
| 判定改为二维 | link 状态 × 访问模式，四个格子分别定级 |
| 引入 link count | lsof 加字段 `k`；`k==0` 视为权威的「已 unlink」 |
| 增加能力探测 | 若某卷出现「stat 为 ENOENT 但 k>=1」，标记该卷不提供 link count，并在报告里说明判定依赖路径校验 |
| 卸载改 `eject` | 可移动/外接卷用 `diskutil eject`，其余用 `unmount` |
| 超时提到 120 秒 | 对齐手册的「最多 1 分钟」 |
| 强卸载加锁 | 存在可写句柄时拒绝 `--force-unmount`，不提供绕过 |
| `txt` 句柄补测映射保护位 | 对 `fd=txt` 的 REG 句柄调 `proc_pidinfo(PROC_PIDREGIONPATHINFO)`，`VM_PROT_WRITE` 位存在即视为可写；否则 mmap 写入会被判成只读，`mmap+unlink` 更会误报 SAFE |
| 强卸载的理由改写 | 从「会毁盘」改为「会让正在写的程序丢数据，而且它可能不知道」——前者实测不成立 |
